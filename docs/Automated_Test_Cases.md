# Automated Test Cases – Strategy, Dependencies and Traceability

Automation of **scenario 1** (form creation and configuration) and **scenario 4** (mandatory fields) of the
assessment, executed with the administrator account only. Suite: `suites/planradar.xml` (generated by `tools/gen_suites.py`, catalog in [test-catalog/planradar.md](test-catalog/planradar.md)); run with `mvn test` or from the test dashboard (`python runner/server.py`, http://127.0.0.1:8090). Run modes: `-Drun.mode=normal`
(default, visible browser), `fast` (headless, used in CI) and `demo` (visible, maximized, each action highlighted and
followed by a `demo.step.delay.ms` pause for an audience); waits and assertions are identical in all modes (see README).

## A. Strategy

| Item | Value |
|---|---|
| Objectives | S1: a form with several field types is created and every configured property persists (builder, lists, project). S4: a ticket cannot be saved while a mandatory field is empty – new or existing ticket, text or List field – and saves once it is filled; a per-project override is respected |
| Scope | Form builder, global lists, project form assignment and per-project *Mandatory* override, new and existing tickets |
| Out of scope (automation) | Field permissions per role (scenario 2, needs role accounts) and default values (scenario 3) – both covered by the manual test cases in [02_Test_Cases.md](02_Test_Cases.md) |
| Approach | UI automation through the business workflow (builder → project → ticket), happy path first; every assertion checks an observable outcome (persisted, listed, reopened) |
| Stack | Java 21, Selenium 4.49, TestNG 7.12, Maven, Allure 2.29; Page Object + Flow + Builder |
| Environment | https://www.planradar.com demo account, project "QA Assessment - Form Builder", Chrome latest, 1920×1080 |
| Risks | Shared demo data, UI changes to `data-testid`s, trial limits |
| Entry criteria | Credentials configured; project and Location folder exist; suite compiles |
| Exit criteria | All 9 executed or explicitly BLOCKED; no unexplained failure; every failure classified |

## B. Dependencies

Resolved by `AssessmentFixture`, once per run, by the first test that needs them. A failed dependency is not
retried: every dependent test is skipped as **BLOCKED** (`DEPENDENCY_FAILURE`), unrelated tests keep running.
The live status is written to `<output.dir>/execution-summary.md` (`target/` for a Maven run, `runner/runs/<id>/output/` for a dashboard run).

| ID | Requirement | Existing state | Setup procedure | Needed by |
|---|---|---|---|---|
| DEP-001 | Authentication | Admin account, credentials only in the git-ignored local file | `PlanRadarBaseTest` → `AuthenticationFlow` before **every** test | all |
| DEP-002 | Forms and Lists permission | Account administrator | Open Forms and Lists › Forms | all |
| DEP-003 | Global lists `QA_Assessment_Inspection_Status` (Pass, Fail, Pending) and `QA_Assessment_Inspection_Category` (Electrical, Mechanical, Civil) | Created on first run, reused afterwards | Lists page: create when missing | TC-001 … TC-009 |
| DEP-004 | Form under test `QA_Assessment_Form_<run id>` | New per run | TC-001 builds it; the fixture builds it when TC-001 did not run | TC-002 … TC-009 |
| DEP-005 | Project "QA Assessment - Form Builder" | **Exists** (not created by the suite) | Open from Projects, remember its id | TC-004 … TC-009 |
| DEP-006 | Form assigned to the project | New per run | Project › Forms › Assign form › + › Apply (TC-004 or fixture) | TC-005 … TC-009 |
| DEP-007 | Form selectable when creating a ticket | – | Create Ticket › form selector | TC-005 … TC-009 |
| DEP-008 | Folder "QA Testing Location" selectable as Location | **Exists** | Select it in the new-ticket dialog | TC-005 … TC-009 |

```text
DEP-001 Login → DEP-002 Permission → DEP-003 Lists → DEP-004 Form
   → DEP-005 Project → DEP-006 Assignment → DEP-007 Form selectable → DEP-008 Location → TC-005 … TC-009
```

## C. Test data (`AssessmentData`)

Form `QA_Assessment_Form_<run id>`, description "PlanRadar QA assessment form - run <run id>":

| Field | Type | Mandatory | Default |
|---|---|---|---|
| Title | Predefined (added by PlanRadar) | Yes | – |
| Inspector Name | Short Text | **Yes** | – |
| Inspection Notes | Long Text | No | `Initial inspection` |
| Inspection Date | Date | No | `2026-10-15` |
| Estimated Cost | Decimal | No | `125.50` |
| Inspection Status | List `QA_Assessment_Inspection_Status` | **Yes** | – (must start empty on a new ticket) |
| Inspection Category | List `QA_Assessment_Inspection_Category` | No | `Electrical` |
| Follow-up Required | Checkbox | No | checked |

Ticket titles: `QA_Assessment <TC id> <run id>-<n>` (unique per run and test case).

## D. Test cases

Common precondition: fresh browser, logged in as administrator (DEP-001). *Actual result* and *Status* of the last
run are in [04_Test_Execution_Report.md](04_Test_Execution_Report.md).

### Scenario 1 – Form creation and configuration · `FormBuilderTest`

| ID | Title | Priority | Preconditions | Steps | Expected result |
|---|---|---|---|---|---|
| TC-001 | Create a new form with several field types | P0 | DEP-002, DEP-003 | 1. Forms and Lists › Forms › Create a new form 2. Enter the unique name and description 3. Add the 7 fields and configure name, list, mandatory and default of each 4. Save 5. Search the list and reopen the form | Form listed; reopened form shows name, description, the predefined Title (not deletable) and all 7 custom fields |
| TC-002 | Verify every field configuration is saved | P0 | DEP-004 | 1. Open the form 2. Open the properties of each field | For every field: name, type, *Mandatory* checkbox, `*` marker on the canvas and default value match the test data |
| TC-003 | Verify List field configuration (list, values, default) | P1 | DEP-004 | 1. Lists page: item count of both lists 2. Open each List field's properties | Correct global list assigned; offered values = list values in order; default value as configured (none for Inspection Status) |
| TC-004 | Assign the form to the project and verify it is available for tickets | P0 | DEP-004, DEP-005 | 1. Project › Forms › Assign form › + 2. Check per-project *Mandatory* flag and list of every field 3. Apply 4. Create Ticket › choose the form | Per-project configuration equals the form's; form listed under the project's forms; selectable in the new-ticket dialog |

### Scenario 4 – Mandatory fields · `MandatoryFieldsTest`

| ID | Title | Priority | Preconditions | Steps | Expected result |
|---|---|---|---|---|---|
| TC-005 | Empty mandatory text field blocks saving | P0 | DEP-006 … 008 | 1. New ticket: Title, Inspection Status = Pass, **Inspector Name empty** 2. Save | Inspector Name marked `*`; validation message next to it; dialog stays open; ticket not listed after discarding |
| TC-006 | Empty mandatory List field blocks saving | P0 | DEP-006 … 008 | 1. New ticket: Title, Inspector Name filled, **Inspection Status empty** (no default) 2. Save | Status starts empty and is marked `*`; validation next to it; dialog stays open; ticket not listed |
| TC-007 | Ticket with all mandatory fields filled is saved | P0 | DEP-006 … 008 | 1. Fill Title, Inspector Name, Inspection Status = Fail 2. Save and close 3. Search and reopen | Dialog closes; ticket listed; Title / Inspector Name / Status persisted; no validation error |
| TC-008 | Clearing a mandatory field on an existing ticket is blocked | P1 | DEP-006 … 008; setup creates a valid ticket | 1. Open the ticket 2. Clear Inspector Name 3. Save 4. Discard changes 5. Reopen | Save blocked with a message next to the field; reopened ticket still has the original value |
| TC-009 | A project-level Mandatory override is respected | P1 | DEP-006 … 008 | 1. Project › Forms › form configuration: Inspector Name **not** mandatory › Apply 2. New ticket without Inspector Name › Save and close 3. Restore the flag › Apply | No `*` on Inspector Name; ticket saves and is listed; project setting restored (verified) |

## F. Reporting

- `target/execution-summary.md` (or `runner/runs/<id>/output/`) – dependencies and every test case with status and classification
  (`DEPENDENCY_FAILURE`, `SUSPECTED_DEFECT`, `AUTOMATION_DEFECT`, `ENVIRONMENT_ERROR`, `CONFIGURATION_ERROR`).
- `target/screenshots/<TC id>_<status>_<time>.png` – final state of every test.
- `target/allure-results` → `allure-report/` (`mvn allure:report` or `python tools/allure_report.py`; the test dashboard also builds a single-file report per run):
  description and covered manual cases (tags) per test, UI actions as steps, every assertion as a step with
  Expected / Actual, test-data and run-context attachments, final screenshot; on failure also page HTML and browser
  console. *Categories* group failures by the classification above; *Environment* shows run id, form, browser
  version and Selenium version.
